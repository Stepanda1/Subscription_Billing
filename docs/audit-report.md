## Подтверждённые проблемы

| Приоритет | Ошибка и воспроизведение | Исправление и защита от повторения |
|---|---|---|
| P1 | API публикует оплату на чистом брокере до первого запуска worker. В БД остаётся неактивная подписка, outbox уже пуст, очереди или нужной привязки нет. Publisher confirm не гарантирует маршрутизацию в очередь. | `BindQueue` привязывает очередь к самому message exchange `subscription-activation-paid`. `AutoStart` и `DeployPublishTopology` объявляют топологию до готовности bus. `verify-cold-start.ps1` проверяет сохранность сообщения до worker и после перезапуска брокера. |
| P2 | `Payment.PaidAt` и `SubscriptionPaidEvent.PaidAt` создавались разными вызовами часов. Тест фактического broker delivery получил `22:38:20.9065490Z` в БД и `22:38:21.0625303Z` в событии. | Одно время UTC с точностью до микросекунды используется в платеже и событии. Новый xUnit-тест сравнивает сохранённое время с реально доставленным событием. |
| P2 | Compose требовал здоровый RabbitMQ перед запуском API. Это блокировало холодный старт сервиса, способного принять запись в outbox без брокера. | У API сохранена зависимость от успешной миграции; зависимость от RabbitMQ снята. Контракт Compose и реальный запуск без брокера проверяются автоматически. |
| P2 | Для PostgreSQL и RabbitMQ отсутствовала политика перезапуска. При начале аудита оба контейнера были остановлены, а API и worker работали без зависимостей. | Для обоих сервисов задан `restart: unless-stopped`. Контракт проверяется по разрешённой конфигурации Compose. Перезапуск Docker Desktop или компьютера в ходе аудита не выполнялся. |

У потери сообщения были две причины. `BindQueue(exchangeName, queueName)` объявляет
привязку указанного exchange к очереди и сам не связывает его с другим message
exchange. Кроме того, EF outbox в используемой версии MassTransit доставляет
сохранённое сообщение через `GetSendEndpoint(destination)`, поэтому необходимая
publish-топология должна существовать заранее. Обе части исправлены с сохранением
существующих имён exchange/queue и формата события.
[Исходный код outbox 8.3.6](https://github.com/MassTransit/MassTransit/blob/v8.3.6/src/Persistence/MassTransit.EntityFrameworkCoreIntegration/EntityFrameworkCoreIntegration/BusOutboxDeliveryService.cs),
[реализация BindQueue 8.3.6](https://github.com/MassTransit/MassTransit/blob/v8.3.6/src/Transports/MassTransit.RabbitMqTransport/RabbitMqTransport/Configuration/Topology/ExchangeToQueueBindingPublishTopologySpecification.cs).

Точность времени учтена явно: `DateTime` поддерживает 100 нс, а PostgreSQL
timestamp хранит микросекунды. Простое использование одного `DateTime.UtcNow`
без нормализации оставило бы расхождение после чтения из БД.
[Документация Npgsql](https://www.npgsql.org/doc/types/datetime.html).

## Проверки транзакций и идемпотентности

Новых нарушений атомарности или идемпотентности в проверенных сценариях не обнаружено.
Добавлены девять xUnit-кейсов поверх прежних 17:

- Время платежа в доставленном событии совпадает с PostgreSQL.
- Отмена после INSERT платежа откатывает платёж, подписку и ключ; повтор разрешён.
- Исключение после успешного COMMIT моделирует потерю подтверждения: повтор возвращает
  сохранённый ответ и не создаёт вторую оплату.
- 20 одновременных запросов с одним ключом и разными тарифами имеют одного победителя;
  другой payload получает `409`.
- Отмена запроса, ожидающего advisory lock, освобождает транзакцию и не резервирует ключ.
- 24 доставки с 12 message IDs проверяют транспортные и бизнес-дубли через inbox.
- Неверная сумма отправляет событие в error queue без активации.
- Отсутствующий платёж отправляет событие в error queue без активации.
- Ошибка после UPDATE активации откатывает его вместе с inbox; повтор успешно
  фиксирует активацию и consumed-состояние в одной транзакции.

Тестовый host использует настоящий PostgreSQL и RabbitMQ. Исключения и отмена
внедряются EF-интерцепторами в конкретных точках транзакции. БД `billing_tests`
отделена от приложения. Каждому запуску назначается новая RabbitMQ-топология,
которая удаляется после остановки host, чтобы сообщения предыдущего запуска
не попадали в пересозданную БД.

Smoke-проверка теперь сравнивает полный ответ replay после перезапуска API.
Проверки содержимого вынесены из catch повторных подключений, чтобы последующий
успешный ответ не скрывал уже полученный неверный ответ. Добавлен отказ PostgreSQL:
readiness должен вернуть `503`, liveness остаётся `200`. Проверка учитывает
стандартный таймаут подключения Npgsql.

## Повторение проверок

Из корня репозитория:

```sh
dotnet build "Subscription & Billing.sln" --no-restore -c Release
python -m unittest discover -s tests -p 'test_*.py'
docker compose --profile test run --build --rm tests
pwsh ./scripts/verify.ps1
```

Для первого build необходим restore. `verify-cold-start.ps1` запускается на свежем
локальном/CI Compose-проекте: он сам собирает API и worker, останавливает broker/worker
и проверяет начальное создание очереди. Сценарий включён в GitHub Actions перед
запуском полного стека. На существующих volumes прежняя топология могла бы скрыть
проверяемую регрессию. Скрипты учитывают `COMPOSE_FILE` и `COMPOSE_PROJECT_NAME`.

## Практические границы

Исправление предотвращает новые потери. События, ранее удалённые из outbox после
неудачной маршрутизации, автоматически не восстанавливаются: нужна отдельная сверка
сохранённых оплат с неактивными подписками. Аудит не изменял данные существующего стека.

Проект сохраняет прежнюю модель симулированной оплаты. Провайдер платежей,
авторизация, возвраты, продление подписок и отказоустойчивый кластер брокера
остаются дальнейшими задачами. Результат аудита относится к проверенным сценариям
текущего кода и конфигурации.
